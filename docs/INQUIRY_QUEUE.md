# Основа единой очереди обращений

## Дополнение 01.10.2026: обратный контакт в ручной CRM

В `/chats/new` и обработке `/chats/{id}` добавлен необязательный телефон/email.
Сервер ограничивает ввод 254 символами, проверяет email либо телефон из 7–15
цифр с необязательным `+`, убирает внешние пробелы, форматирование телефона
и приводит email к нижнему регистру. Используется существующий `reply_contact`;
новая миграция не нужна. Пустой ввод сохраняется как `null`. Отсутствующее поле
старой формы не изменяет контакт уже существующей заявки.

Права `LEAD_VIEW/CREATE/EDIT`, tenant/branch scope и optimistic version сохранены.
Нормализованный контакт входит в creation hash: повтор того же запроса не создаёт
дубль; другой контакт при том же ключе отклоняется. Контакт не включается в
метаданные аудита. Значение из заявки сайта доступно для исправления сотруднику
с правом редактирования; внешние сообщения и финансовые операции не выполняются.

Проверка: `node scripts/inquiry-reply-contact-mock.cjs` исполняет реальную
валидацию, сервис, server action и форму с allowlist mock-зависимостей.
Сценарии включают создание/правку/очистку, старые формы, повторную отправку,
конфликт версии, tenant/branch isolation, права и отсутствие контакта в аудите.
Реальная БД, клиентские данные и внешние API не используются. Это локальный
блок кода; применение в deployment и DB/E2E-приёмка этим тестом не подтверждаются.

Локальный функциональный блок поверх `review/next-block` / `0a470548…`, после
сохранённых документов аренды. Код не опубликован, новая схема не применена.

## Повторное использование и объём

На исходной базе моделей Lead/Inquiry/Chat и очереди не было. Переиспользованы
существующие `LEAD_VIEW/CREATE/EDIT/ASSIGN/CLOSE`, tenant/branch access, аудит,
каталог вариантов и функции timezone. Созданы только `Inquiry` и `InquiryItem`;
параллельных Lead и Chat-сущностей нет. `LEAD_CONVERT_TO_ORDER` остаётся
зарезервированным правом без реализованной операции.

«Чаты» ведёт на `/chats`: список, фильтры (источник/филиал/статус/назначено мне),
постраничный вывод по 50 и ручное создание `/chats/new`. Карточка `/chats/{id}`
позволяет менять запрос, период, статус, ответственного и следующее действие.
Внутренний WhatsApp lookup сохранён на `/whatsapp` и доступен из очереди.
Это ещё не лента сообщений: внешние аккаунты, события, отправка сообщений,
webhooks, LLM и автоматическая доставка не подключены.

## Разумные defaults первого блока

- Источник: «В магазине» по умолчанию; доступны сайт, Telegram, WhatsApp,
  телефон и другое. Это ручная отметка происхождения, не доказательство
  получения сообщения из подключённого канала.
- Один обязательный филиал. После создания источник и филиал не меняются.
- Статусы: `NEW`, `IN_PROGRESS`, `WAITING_CUSTOMER`, `CLOSED`; старт `NEW`.
  Закрытие и повторное открытие требуют `LEAD_EDIT` и `LEAD_CLOSE`.
- Ответственный по умолчанию не назначен. Изменение назначения, включая
  назначение себе/снятие, требует `LEAD_ASSIGN`. Новый ответственный — активный
  сотрудник той же организации с доступом к филиалу и `LEAD_VIEW/LEAD_EDIT`.
  Утрата сотрудником доступа впоследствии не вызывает скрытого переназначения.
- Тема обязательна; имя/обращение к клиенту, описание и пожелание по размеру
  необязательны. Телефон, email, паспорт, клиентская карточка не требуются.
- До 20 вариантов каталога на этапе регистрации; сохраняются SKU, название
  и размер. Поиск даёт до 50 вариантов; каталог доступен по `CATALOG_VIEW`.
  В этом минимальном блоке выбор вариантов после создания не меняется;
  новые пожелания можно зафиксировать текстом. Количество/цена/доступность
  не обещаются и не резервируются.
- Период: обе даты или ни одной, конец позже начала. Даты и срок следующего
  действия вводятся/отображаются в timezone филиала. Следующее действие
  необязательно; указание срока требует текста действия. Уведомлений нет.
- Фильтр филиала/товаров перед созданием перезагружает форму; сначала
  выбирают фильтр, затем заполняют заявку. Несохранённый ввод при смене фильтра
  сбрасывается, что явно указано в интерфейсе.

## Хранение и доступ

Inquiry хранит контекст, источник/статус, запрос/даты, ответственного, следующее
действие/срок, автора, версию и ключ/хэш создания. InquiryItem связан с вариантом
каталога; исторические labels сохранены отдельно. Создание с тем же UUID и
payload возвращает тот же id; несовпадающий payload отклоняется. Обновление
проверяет version и атомарно увеличивает её; устаревшая форма не затирает работу
другого сотрудника. Аудит и изменение записываются в одной транзакции; тексты
клиента в audit metadata не копируются.

Черновик `20260930160000_inquiry_queue/migration.sql` содержит enum, таблицы,
FK, индексы, tenant-context guards, RLS без публичных policies и отзыв прав
PUBLIC/anon/authenticated. При отсутствии таблицы страницы показывают, что
очередь ещё не включена. Runtime не выполняет DDL.

Заявка не создаёт Customer, Order, CapacityAllocation, ProductInstance,
StockLevel, движение или платёж. Публичных endpoints в этом блоке нет.
Будущие адаптеры сайта/Telegram/WhatsApp должны вызывать общий сервис с
проверенным контекстом и отдельным ключом доставки; публичный доступ нельзя
получать выдачей клиенту привилегий текущего staff action.

## Включение и отложенная приёмка

Prisma history gap `20260930130000_product_sheet_import` остаётся блокером
применения/выпуска; предыдущий черновик документов также не применён.
Нужны отдельное согласование миграций и проверка на изолированной БД.
Gate хранения персональных данных в Казахстане не закрыт; реальные клиентские
данные при разработке не использовались.

На финальной приёмке: создание/повтор запроса, конкурирующее редактирование,
tenant/branch/permission isolation, назначение сотрудника, закрытие/reopen,
timezone/пустой период, сохранность документов аренды и отсутствие любых
заказов/броней/складских/финансовых эффектов. Эти DB/E2E сценарии пока не
объявляются пройденными.
