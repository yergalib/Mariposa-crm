# PILOT outfit conversation

## Functional scope

- The existing central butterfly opens the compact consultant. The owner-enabled
  Preview flag remains unchanged; actual PILOT staff authentication and synthetic
  acknowledgement remain required. No paid API test was performed for this change.
- Three independent slots: dress, shoes, accessory. A bounded structured context
  carries explicit selections, per-slot size/colour/category, shared branch and dates.
  The UI retains the latest four exchanges plus the current message; criteria and
  selected IDs survive this history window. Context is untrusted user input, not
  authority to access products or claim prices/availability.
- Requests for shoes/accessories, refusal, removal, replacement, price clarification
  and completing the selection have separate handling. Selecting a dress offers
  available next steps; no other product is added automatically. Replacing one slot
  keeps the old choice until a replacement is explicitly selected; other slots remain.
- Shoe size is requested separately, never copied from dress size. Category options
  come from the published CRM categories. Search filters category before pagination,
  along with tenant, publication, colour and size. No second catalogue or stock copy.
- Selected variants are revalidated through public CRM services on every turn,
  including branch access, product publication, category/slot membership and current
  availability/price. At most three selection checks plus one catalogue search.
  No model-controlled tool loop. Complete criteria need no model call; incomplete
  dress requests may use one bounded extraction call. Model replies do not create cards.
- Paid model quota is charged only when the provider is actually invoked. Read-only
  selection/refinement clicks use the existing process-local read-pressure limit;
  they do not consume the four-per-minute paid-call allowance. Neither limit is a
  distributed/global budget. The 25-second deadline and no-retry policy remain.

## One inquiry for the selection

The existing InquiryItem relation supports the selected dress plus up to two other
variants without a migration. The public payload keeps variantId and optionally adds
additionalVariantIds (maximum two, duplicates rejected). Every variant is checked for
tenant/publication eligibility inside the transaction. Contact, honeypot, byte limits,
shared DB rate locks and exact-payload idempotency remain. Changed items on an uncertain
retry cannot silently reuse the old key. Client retries retain the exact payload.

The customer explicitly opens the contact form and separately submits it. The contact
does not enter the model dialogue. One inquiry contains all selected items and shared
dates; this does not create an order, payment, reservation or stock movement.

## Limits and verification

There is one item per slot (maximum three total). Generic accessory requests offer real
category buttons. Compatibility/style/occasion attributes are not present in CRM, so
the assistant does not claim an outfit is stylistically compatible. Unknown prices
remain unknown. This is a bounded catalogue consultant, not unrestricted fashion advice.

Mock regressions cover the original repeated-question transcript; dress → shoes →
accessory; independent sizes; shared dates; explicit selection; replacement/refusal;
untrusted IDs/category rejection; category-before-pagination; multi-item inquiry,
publication checks and exact retry behavior. No real inquiry, order, payment, inventory
operation or paid model call was generated by these tests. Live model/browser quality
verification remains outstanding; deployment success is not an end-to-end test.
