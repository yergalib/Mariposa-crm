# Минимальная публичная витрина — локальный код

Решение пользователя от 30 сентября 2026: отдельный переключатель товара
«Показывать на сайте», выбор филиала/размера/дат, заявка сотруднику без
автоматического заказа или брони. Основа: `a9e9391`; исходный checkout не менялся.

## Публикация и контракт

- `Product.showOnWebsite` по умолчанию false, включая существующие строки.
  Переключатель есть в форме создания/редактирования с прежними правами
  CATALOG_CREATE / CATALOG_EDIT. ACTIVE сам по себе ничего не публикует.
- `/showroom` и ровно два маршрута `/api/showroom/catalog` (GET),
  `/api/showroom/inquiries` (POST) доступны без CRM-сессии. Остальные правила
  proxy не расширены; внутренние server actions сохраняют свою авторизацию.
- Tenant задаёт только серверный `STOREFRONT_ORGANIZATION_ID`. Значение не
  устанавливалось: без корректной привязки витрина закрыта. Нет fallback на
  первую организацию, клиентский orgId, cookie или заголовок Host.
- Нужны активная организация и активный `Branch.isPublic`. Отдаются только
  id, название, city, timezone филиала. Товары: showOnWebsite + ACTIVE +
  не архивные + rentable; варианты, размеры и исполнения должны быть активны
  и принадлежать тому же tenant. Товар показывается во всех публичных филиалах;
  наличие считается отдельно по выбранному филиалу. Филиал с нулевым наличием
  не скрывает товар: можно отправить запрос на уточнение.
- DTO варианта: id, название товара, размер, название исполнения,
  действующая RENTAL-цена и булев результат доступности. Цены: филиальная,
  иначе общая; validFrom/validUntil проверяются на текущее время. bigint передаётся
  строкой, отображение суммы повторяет единицы CRM, без расчёта выдуманного
  тарифа/итога за период. Нет цены — «Цену уточнит сотрудник».
- Доступность вычисляет общий `getVariantAvailability`, включая существующие
  правила BULK/SERIALIZED, резервов и буфера. Точные складские количества,
  инвентарные номера и allocation IDs не выдаются.
- Закупка, маржа, поставщики, контакты сотрудников/клиентов, внутренние заметки
  и описание товара не выбираются публичными запросами. Фото только заглушка:
  Storage, оригиналы и signed URLs не используются.
- Минимальный UI: свободный фильтр размера, до 8 вариантов на страницу, до
  100 страниц; выбор города через подпись публичного филиала. Период будущий,
  до 31 дня, начало не далее года вперёд; timezone берётся из филиала.

## Заявка и ограничения

- Один вариант, филиал, период, один телефон или email. Имя, произвольные
  комментарии, документы и платёжные данные не запрашиваются. В форме объяснена
  цель контакта; юридическое согласие и compliance не заявляются.
- Источник WEBSITE, NEW, ответственный не назначен, createdByUserId = null.
  Nullable автор допустим в SQL только для WEBSITE с обратным контактом.
  Сотрудник не подставляется. Контакт виден лишь в существующей защищённой
  карточке очереди с LEAD_VIEW и tenant/branch-проверками; публичного чтения
  обращения нет. Аудит не получает контакт или тело запроса.
- В транзакции повторно проверяются публичные филиал/вариант, нормализуется
  контакт, сохраняется Inquiry + InquiryItem + аудит. Ни заказ, ни резерв,
  ни склад/финансы не изменяются. Ответ содержит только `{ ok: true }`.
- Строгая схема: неизвестные ключи запрещены, UUID/даты/длины проверяются;
  тело читается с реальным лимитом 4096 байт, только JSON. POST требует
  same-origin Origin, cross-site Fetch Metadata отклоняется; CORS не открыт.
- Honeypot. До 30 заявок организации и 3 на нормализованный контакт в час;
  подсчёт и создание под общим PostgreSQL advisory lock, работают между
  процессами. Дополнительный лимит процесса: 120 GET и 30 POST в минуту.
  Это базовая защита от очевидного спама, не полноценная anti-bot/DDoS защита:
  общий лимит можно исчерпать, лимит чтения не глобален между процессами.
- UUID + hash нормализованного payload и существующий unique индекс дают
  идемпотентность. При неопределённом результате сеть/503 форма сохраняет тот
  же payload/key для повтора и не позволяет изменить выбор в активной отправке.
  Перезагрузка страницы теряет ключ: защита от повторов гарантируется для
  повторов с тем же ключом, не для произвольной новой заявки.
- Ответы API no-store; ошибки БД/конфигурации заменены общим сообщением,
  без SQL, stack, контактов и credentials. Страница динамическая, noindex.

## Включение и отложенная проверка

Новый SQL — только файл `20260930180000_public_showroom/migration.sql`:
флаг товара, контакт/nullable автор, индекс и обновлённая проверка контекста.
Прежние SQL-файлы не переписывались. RLS и отсутствие anon/authenticated grants
сохраняются. Новая Prisma-схема требует применения всех согласованных миграций
до выпуска: даже CRM-форма читает новый столбец.

Перед включением отдельно согласовать изолированную БД и миграции, серверную
привязку tenant, публичные филиалы и явно выбранные товары. Никакие значения
env, публикационные флаги в данных или реальные контакты этим этапом не менялись.
Prisma history blocker `20260930130000_product_sheet_import` не исправлен.
Gate хранения персональных данных в Казахстане остаётся нерешённым до реальных
клиентов; сроки хранения/удаления контактов требуют отдельного решения.

На изолированной БД проверить закрытость по умолчанию, чужие/непубличные IDs,
действующие/отсутствующие цены, BULK/SERIALIZED на датах и timezone, сохранение
в очереди без складских последствий, retry/concurrency и лимиты между процессами,
просмотр контакта только уполномоченным сотрудником. SQL/runtime и браузерный
E2E на этом этапе не проверялись; полный аудит остаётся перед запуском.

## Группировка карточек (PILOT UX)

Каталог сначала пагинирует в БД пары productId/executionId, затем загружает все соответствующие размеры. Разные исполнения и одинаковые названия не объединяются по тексту. Одна карточка содержит явный выбор конкретного варианта; до выбора размера цена/наличие не обобщаются, заявка недоступна. После выбора используются цена, доступность и ID именно этого варианта. Цвет показывается только из существующего поля товара; название исполнения сохраняется.

На странице до 8 групп, до 100 страниц. При более чем 256 подходящих вариантах на странице возвращается просьба уточнить размер/название, без скрытого обрезания размеров. Проверки общей CRM-доступности выполняются максимум по две одновременно. Фильтр размера ограничивает варианты внутри групп. Схема БД и данные не изменяются.

Регрессия scripts/showroom-grouping-smoke.cjs проверяет 20 размеров одной группы, отдельные execution/product IDs при одинаковых названиях, вторую страницу без потерь, разные цены/наличие, отсутствие цены, явную передачу variantId и ограничение большого результата. Проверка использует mock DB.
