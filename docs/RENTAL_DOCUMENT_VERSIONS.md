# Сохранённые документы аренды — первый функциональный блок

Локальная реализация поверх `0a4705485a386efccd047b9b68e5d60b59dba221`.
Не опубликована; миграция **не применена**. Это сохранённые неподписанные
документы, не юридически проверенные акты и не электронные подписи.

## Пользовательский сценарий

В карточке аренды открывается «Документы аренды». Пользователь с `ORDER_VIEW`
видит список версий и может открыть конкретную версию для просмотра/печати.
Для сохранения дополнительно нужен `ORDER_EDIT` и доступ к филиалу заказа.
Новая версия после первой требует причины; старая версия не редактируется.
Документ не меняет заказ, выдачу, возврат, резерв, склад или финансы.

Форма блокируется на время отправки. UUID запроса обеспечивает повторное
получение той же версии при повторном клике/сетевом повторе; изменение payload
того же запроса отклоняется. При сохранении другой версии из соседней вкладки
устаревшая форма требует обновления страницы.

Список показывает последние 100 версий; ранее сохранённые ссылки продолжают
работать. `/orders/{orderId}/documents/{documentId}` читает snapshot, а не живые
имена/количества заказа. Печать браузерная, серверного PDF и Storage нет.

## Данные и целостность

`RentalDocumentVersion` хранит tenant/branch/order, номер версии, автора/время,
версию схемы и шаблона, JSONB snapshot, SHA-256, UUID запроса и причину.
Снимок формируется из явного списка полей в Serializable-транзакции; сохранение
и минимальный audit event атомарны. Нумерация защищена advisory lock и unique
constraint; конфликт сериализации/нумерации повторяет всю транзакцию до 3 раз.

Snapshot включает имя клиента без контактов, номер/русский статус заказа,
филиал/timezone, даты, позиции/SKU, режим учёта, количества, даты передачи,
идентификаторы физических экземпляров только для SERIALIZED, результаты и
примечания осмотра, ссылки на исходные allocation/resolution для трассировки.
Финансы, цены, депозит, адреса, телефоны, внутренние комментарии не выбираются.
Причина и примечания осмотра видны в документе: сотрудники не должны вносить
в них лишние персональные/финансовые сведения.

Это согласованный снимок чтения при сохранении, не реконструкция заказа
задним числом на дату выдачи. Утрата отделена от возвращённого количества.
Старый динамический рабочий лист остаётся доступен отдельно.

Hash вычисляется по каноническому JSON (порядок ключей JSONB несущественен)
и проверяется перед отображением. Он выявляет несоответствие содержимого, но
не удостоверяет личность/согласие и не является электронной подписью.
Для `templateVersion=1` оставляется `RentalDocumentV1`; новый шаблон должен
получить новую версию с сохранением reader/renderer предыдущего формата.
Гарантия относится к сохранённым данным, не к идентичности PDF/браузерной
пагинации во времени.

## Миграция и включение

Черновик: `20260930150000_rental_document_versions/migration.sql`.
Включает FK/tenant-context guard, unique/indexes, RLS без публичных policies,
отзыв доступа PUBLIC/anon/authenticated и запрет UPDATE/DELETE/TRUNCATE версий.
Удаление по требованиям хранения/ПД потребует отдельного согласованного
процесса; UI не даёт удалить историю.

Существующий пропуск `20260930130000_product_sheet_import` в Prisma history
остаётся блокером применения/выпуска. Этот блок **не исправляет** его. Если
таблица документов отсутствует, новые страницы показывают сообщение о том,
что сохранение ещё не включено; скрытого DDL/создания таблицы в runtime нет.

Перед включением: согласовать восстановление истории Prisma и применение
новой миграции, проверить её на изолированной БД, принять сценарии сохранения,
повтора/конкуренции, tenant/branch/permission isolation, неизменности версии и
печати. Полный security/E2E аудит отложен до приёмки перед запуском. Проверки
DDL/транзакций с реальной БД на этапе разработки не выполнялись. Gate хранения
персональных данных в Казахстане из master roadmap остаётся нерешённым.
