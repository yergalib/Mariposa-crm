# Цветовые исполнения: контракт сайта с CRM

Проверено по коду сайта `0239b3a`, 2026-10-05. Это состояние данной ветки, а не вывод о параллельных изменениях CRM или реальной БД. Требование владельца: у разных исполнений модели могут отличаться цены, разрешения аренды/продажи и публикация. Источник данных — только CRM.

## Уже поддерживается

- `ProductVariant` связывает модель, исполнение и размер. `ProductPrice` относится к конкретному variant ID, типу RENTAL/SALE, филиалу и периоду действия (`prisma/schema.prisma`). Разные исполнения могут иметь разные цены без отдельной таблицы сайта.
- `lib/showroom/service.ts` группирует каталог по `productId + executionId`; карточка возвращает размеры только выбранного исполнения. URL, избранное и сравнение сохраняют execution ID. Выбор проверяет конкретный variant ID через общую `getVariantAvailability` CRM.
- Витрина сейчас арендная: читает только действующие RENTAL-цены, предпочитает цену филиала общей цене. При отсутствии возвращает `null`, UI предлагает уточнить стоимость. Наличие цены не является разрешением аренды/продажи. Цена продажи и покупка на сайте не реализованы.
- Фото в CRM имеют привязки к модели/исполнению/варианту, но публичные DTO фото пока не возвращают: на сайте заглушки. Ни URL хранилища, ни storageKey клиенту не раскрываются.

## Что отсутствует и требуется от основной ветки CRM

1. У `ProductExecution` сейчас только `isActive`; `showOnWebsite`, `isRentable`, `isSellable` находятся у `Product`. Нельзя скрыть только один активный цвет или запретить только его аренду. Публичный фильтр пропускает все активные исполнения опубликованной арендной модели. Это ограничение, а не готовая поддержка нового требования.
2. CRM должна определить авторитетные поля/эффективные разрешения исполнения и правила наследования для `executionId = null`. Предложение для согласования с CRM: флаги модели остаются общим запретом, исполнение может дополнительно запретить публикацию/операцию; публикация нового исполнения требует явного разрешения. Не вводить независимый список разрешений на сайте и не трактовать `isActive` как публикацию.
3. Excel-импорт должен адресовать устойчивые variant/execution ID, проверять tenant и принадлежность модели, однозначно трактовать пустые ячейки и конфликтующие строки одного исполнения. В текущем `lib/catalog/price-workbook.ts` разрешения проверяются только на модели. Изменения импорта/данных выполняет основная CRM-ветка.
4. Общие CRM-проверки заказа/продажи должны учитывать эффективные разрешения исполнения. Места текущих проверок: `lib/orders/{management,mobile,queries}.ts`, `lib/sales/{lifecycle,mobile}.ts`. Один фильтр сайта не обеспечивает бизнес-правило.
5. После предоставления схемы и общей политики CRM сайт подключит её в `variants()` и во всех повторных проверках карточек, выбора, избранного, помощника и заявки. Понадобятся тесты: два цвета одной модели с противоположными флагами; прямой URL/variant ID скрытого цвета; потеря разрешения после выбора; запрет родительской модели; исполнение без override. SALE-only каталог/DTO — отдельное решение, текущий сценарий остаётся арендным и inquiry-only.
6. Для настоящих фото нужен утверждённый CRM-контракт публичной выдачи: приоритет variant/execution/model, разрешение использования общей фотографии, ACTIVE/not-deleted, tenant/publication checks и безопасный URL. До него сохраняются заглушки, без заимствования фото соседнего цвета.

Новая миграция или реализация полей в этой ветке не создаётся: это пересеклось бы с работой основной CRM-ветки. Применение схемы остаётся отдельным согласованным действием; известный Prisma history blocker не обходится. Финансовые внутренние поля, контакты и заметки в публичный DTO не добавляются.
